# 4. ARCHITECTURAL PRINCIPLE

## OFFLINE-FIRST IS MANDATORY

Do not build the online version first and add offline support afterward.

Every business operation must first work against the local data layer.

The application must follow this rule:

USER ACTION
↓
DOMAIN VALIDATION
↓
LOCAL DATABASE TRANSACTION
↓
LOCAL UI UPDATE
↓
OUTBOX SYNC QUEUE
↓
CLOUD SYNCHRONIZATION WHEN AVAILABLE

Cloud synchronization must never be required to create an invoice, quotation, customer, product, or company profile in an existing local workspace.

## Source of truth

For the current device and workspace, the local database is the source of truth for responsive UI operations.

The server is the authoritative shared source for synchronized workspace data.

The synchronization layer must reconcile the two without silently losing user data.

## Important constraints

* Never store sensitive Supabase service-role keys in Electron or browser code.

* Never trust client-side prices, taxes, discounts, or authorization claims.

* Recalculate financial totals using trusted business logic.

* Do not use floating-point arithmetic for monetary calculations.

* Use integer minor units or a decimal arithmetic strategy.

* Never use JavaScript Date objects as the sole source of truth for financial document dates.

* Preserve audit history for finalized documents.

* Do not silently overwrite conflicting records.

* Do not use localStorage as the primary business database.

* Do not expose arbitrary Electron IPC methods to the renderer.

# 10. SYNCHRONIZATION ENGINE

Implement a robust bidirectional synchronization system.

## Offline workflow

User creates an invoice.
↓
Validate input locally.
↓
Calculate totals locally.
↓
Save invoice to IndexedDB.
↓
Save line items in a local transaction.
↓
Create an outbox operation.
↓
Update the UI immediately.
↓
Display “Pending sync.”

## Online workflow

Detect connectivity.
↓
Authenticate the workspace.
↓
Push pending local changes.
↓
Server validates permissions and data.
↓
Apply idempotent server changes.
↓
Pull remote changes after the last known cursor.
↓
Apply changes locally in transactions.
↓
Update sync metadata.
↓
Display “Synced.”

## Synchronization requirements

* Operation IDs for idempotency.

* Device IDs.

* Workspace IDs.

* Retry with exponential backoff.

* Failed-operation tracking.

* Sync cursors or checkpoints.

* Batch processing.

* Transactional local updates.

* Sync progress indicators.

* Last-synced timestamp.

* Manual sync button.

* Automatic synchronization.

* Network recovery handling.

* Authentication-expiry handling.

* Partial failure handling.

* Schema-version compatibility.

* No duplicate invoices after retries.

* No silent data loss.

Do not rely exclusively on timestamps to resolve every conflict.

Document how the system handles concurrent edits.

# 11. CONFLICT RESOLUTION

Implement a conflict-resolution framework.

Conflict types:

1. Customer edited on two devices.

2. Product price edited on two devices.

3. Draft invoice edited on two devices.

4. Quotation edited while offline and modified online.

5. Record deleted on one device and updated on another.

6. Two devices attempt to finalize a document.

7. Two devices attempt to allocate the same invoice number.

Rules:

* Draft records may use a documented merge strategy.

* Finalized financial documents must be immutable or require controlled correction workflows.

* Conflicting financial changes must not be silently merged.

* Present a conflict-resolution interface where user intervention is required.

* Preserve both conflicting versions where appropriate.

* Log every conflict-resolution action.

* Prevent duplicate finalized invoice numbers through server-side allocation.

* Explain behavior when two devices are offline and later reconnect.

Provide state diagrams and sequence diagrams.

## 4. Essential database design

Use UUIDs for synchronized entities. Keep document numbers separate from entity IDs.

## Core database relationships

Simplified relational model for the MVP

workspaces

id · name · owner_id

customers

id · workspace_id · name · GSTIN

quotations

id · customer_id · status · total_minor

quotation_items

id · quotation_id · description · quantity · unit_price_minor

invoices

id · quotation_id? · customer_id · status · total_minor

payments

id · invoice_id · amount_minor · payment_date

sync_operations

id · entity_id · operation · status · retry_count

### Money representation

Use integer minor units or a decimal library.

For example, for Indian rupees:

TypeScript

```
type Money = {
  currency: "INR";
  minorUnits: bigint;
};
```

A value of ₹1,250.50 would be represented as `125050` paise when using integer paise.

For production financial software, ensure that serialization, database types, calculations, rounding, and PDF formatting are consistent.

### One critical correction to your original roadmap

A truly offline-capable Electron application should not depend on the Next.js development server or a live Vercel website to operate. The packaged Electron application must include the necessary frontend assets and load them locally.

For your MVP, I recommend:

Electron + Next.js + Dexie.js + shared domain packages + Supabase sync, with the local database designed first and cloud functionality added through repositories and synchronization services.
