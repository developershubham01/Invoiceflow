   234→# 4. ARCHITECTURAL PRINCIPLE
   235→
   236→## OFFLINE-FIRST IS MANDATORY
   237→
   238→Do not build the online version first and add offline support afterward.
   239→
   240→Every business operation must first work against the local data layer.
   241→
   242→The application must follow this rule:
   243→
   244→USER ACTION
   245→↓
   246→DOMAIN VALIDATION
   247→↓
   248→LOCAL DATABASE TRANSACTION
   249→↓
   250→LOCAL UI UPDATE
   251→↓
   252→OUTBOX SYNC QUEUE
   253→↓
   254→CLOUD SYNCHRONIZATION WHEN AVAILABLE
   255→
   256→Cloud synchronization must never be required to create an invoice, quotation, customer, product, or company profile in an existing local workspace.
   257→
   258→## Source of truth
   259→
   260→For the current device and workspace, the local database is the source of truth for responsive UI operations.
   261→
   262→The server is the authoritative shared source for synchronized workspace data.
   263→
   264→The synchronization layer must reconcile the two without silently losing user data.
   265→
   266→## Important constraints
   267→
   268→* Never store sensitive Supabase service-role keys in Electron or browser code.
   269→
   270→* Never trust client-side prices, taxes, discounts, or authorization claims.
   271→
   272→* Recalculate financial totals using trusted business logic.
   273→
   274→* Do not use floating-point arithmetic for monetary calculations.
   275→
   276→* Use integer minor units or a decimal arithmetic strategy.
   277→
   278→* Never use JavaScript Date objects as the sole source of truth for financial document dates.
   279→
   280→* Preserve audit history for finalized documents.
   281→
   282→* Do not silently overwrite conflicting records.
   283→
   284→* Do not use localStorage as the primary business database.
   285→
   286→* Do not expose arbitrary Electron IPC methods to the renderer.

   900→
   901→Implement a robust bidirectional synchronization system.
   902→
   903→## Offline workflow
   904→
   905→User creates an invoice.
   906→↓
   907→Validate input locally.
   908→↓
   909→Calculate totals locally.
   910→↓
   911→Save invoice to IndexedDB.
   912→↓
   913→Save line items in a local transaction.
   914→↓
   915→Create an outbox operation.
   916→↓
   917→Update the UI immediately.
   918→↓
   919→Display “Pending sync.”
   920→
   921→## Online workflow
   922→
   923→Detect connectivity.
   924→↓
   925→Authenticate the workspace.
   926→↓
   927→Push pending local changes.
   928→↓
   929→Server validates permissions and data.
   930→↓
   931→Apply idempotent server changes.
   932→↓
   933→Pull remote changes after the last known cursor.
   934→↓
   935→Apply changes locally in transactions.
   936→↓
   937→Update sync metadata.
   938→↓
   939→Display “Synced.”
   940→

   943→* Operation IDs for idempotency.
   944→
   945→* Device IDs.

   947→* Workspace IDs.
   948→
   949→* Retry with exponential backoff.
   950→
   951→* Failed-operation tracking.
   952→
   953→* Sync cursors or checkpoints.
   954→
   955→* Batch processing.
   956→
   957→* Transactional local updates.
   958→
   959→* Sync progress indicators.
   960→
   961→* Last-synced timestamp.
   962→
   963→* Manual sync button.
   964→
   965→* Automatic synchronization.
   966→
   967→* Network recovery handling.
   968→
   969→* Authentication-expiry handling.
   970→
   971→* Partial failure handling.
   972→
   973→* Schema-version compatibility.
   974→
   975→* No duplicate invoices after retries.

   985→# 11. CONFLICT RESOLUTION
   986→
   987→Implement a conflict-resolution framework.
   988→
   989→Conflict types:
   990→
   991→1. Customer edited on two devices.
   992→
   993→2. Product price edited on two devices.
   994→
   995→3. Draft invoice edited on two devices.
   996→
   997→4. Quotation edited while offline and modified online.
   998→
   999→5. Record deleted on one device and updated on another.
  1000→
  1001→6. Two devices attempt to finalize a document.
  1002→
  1003→7. Two devices attempt to allocate the same invoice number.
  1004→
  1005→Rules:
  1006→
  1007→* Draft records may use a documented merge strategy.
  1008→
  1009→* Finalized financial documents must be immutable or require controlled correction workflows.
  1010→
  1011→* Conflicting financial changes must not be silently merged.
  1012→
  1013→* Present a conflict-resolution interface where user intervention is required.
  1014→
  1015→* Preserve both conflicting versions where appropriate.
  1016→
  1017→* Log every conflict-resolution action.
  1018→
  1019→* Prevent duplicate finalized invoice numbers through server-side allocation.
  1020→
  1021→* Explain behavior when two devices are offline and later reconnect.
  1022→
  1023→Provide state diagrams and sequence diagrams.

  1933→### Money representation
  1934→
  1935→Use integer minor units or a decimal library.
